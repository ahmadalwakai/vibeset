# Initial native beta originals

`originals.json` contains three actual reviewed generated designs, with exact validated specs, bilingual names/descriptions, taxonomy and spec/wallpaper hashes. No DEV account, theme ID, counter or sample fixture is imported. The system-only `native-beta-content` service creates ownerless **drafts** with fresh DB IDs and transactionally audits each import. It serializes concurrent imports, reuses identical rows and refuses conflicting/edited originals. Existing status transitions perform approval; existing `publishTheme` performs publication.

Run the operator from the repository root with credentials securely injected into the child process. It does not load dotenv, accept connection strings in arguments, create accounts or log credentials. Mutation commands reject every database except the explicitly reviewed MAIN endpoint/database and production site; tests exercise the service only on an isolated TEST endpoint.

```sh
npx --no-install tsx --conditions=react-server scripts/prepare-native-beta.ts check
npx --no-install tsx --conditions=react-server scripts/prepare-native-beta.ts stage --cache-refresh=manual
# Review and commit the generated plan, manifest and all 21 public files; deploy them first.
npx --no-install tsx --conditions=react-server scripts/prepare-native-beta.ts publish --cache-refresh=manual
```

`stage` seeds taxonomy/default settings using existing services, imports/approves the three originals, and records their fresh IDs, exact spec hashes, version **1** and one attempt UUID in `publication-plan.json`. It renders actual files under canonical `public/themes/{id}/v1/{attempt}/…` paths and writes `publication.json` with MIME/size/SHA-256 for all 21 objects. Once written, metadata/files are append-only: a differing rerender or changed plan fails instead of overwriting. Commit both JSON files and all public assets so future deployments retain them. Stage does not mark anything published.

`publish` requires the configured CDN origin to be the actual public HTTPS deployment origin, checks the plan against current DB identity/state, and verifies **every** deployed file before publishing the first theme. The injected static storage adapter rechecks exact regenerated bytes and live HTTP bytes during canonical publication. Redirects, MIME/length/hash mismatches or missing objects fail. No status SQL or fake DTO is used. A failed or uncertain DB commit preserves immutable files; inspect the DB and retry the same plan without forcing a new version. The tool never runs static object deletion or old-version cleanup.

Cache refresh defaults to the existing authenticated internal API. Explicit `--cache-refresh=manual` makes no cache-refresh network request and returns `cacheRefresh: "pending"` plus the exact deduplicated `pendingTags`; it never claims completion. The operator must invalidate those tags through the existing authenticated Vercel CLI (`vercel cache invalidate --tag … --project vibeset --scope vibeset1 --yes`) and then verify the actual public API/detail/download responses. The production internal secret must not be rotated for this operation.

This is a narrow first-beta publication exception while R2 is unavailable. Uploads and ordinary future publications retain the existing R2 path. The native live catalogue/CDN preflight remains unchanged, and three originals do not establish the separate 300-theme public launch checklist. Later R2 migration must copy and verify these exact immutable keys before changing the public CDN origin; do not silently drop the static files or rewrite published asset metadata.
