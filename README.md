# Vibeset

P00–P02 foundations: Next.js 16 with Cache Components, React 19.2, Chakra UI v3, an English/Arabic site shell, Neon/Drizzle schema, Better Auth core and validated ThemeSpec tokens. Catalog, authentication screens and Studio arrive in later phases.

## Local development

Use Node 24 (`.nvmrc`), then run:

```sh
npm ci
npm run chakra:typegen
npm run dev
```

Open http://localhost:3000 for English or http://localhost:3000/ar for Arabic. The temporary Home provides the translated hero and app shell. Locale switching preserves the current path and query. Mobile has a five-tab bottom bar; desktop uses the header navigation. Destination pages are implemented in their ordered phases and currently show the localized 404.

For a fresh checkout, copy `.env.example` to `.env.local` and supply the public site/CDN URLs for the shell. Supply real Neon URLs, Better Auth URL/secret, IP hash salt, cron secret and internal API secret before using the database/auth modules. Server configuration is validated when its module is imported; missing values produce key-specific errors. Credentials are never checked into this repository.

## P01 database and auth core

The Neon `vibeset` project is in AWS London. `main` remains empty; both reviewed migrations are applied to `dev`, and `test` was branched from that migrated development state. Local `.env.local` uses `dev` for the app and the separate `test` branch for integration tests. It contains fresh local secrets and is ignored by Git.

The migrations create 20 tables:

- Auth: `user`, `session`, `account`, `verification`, `rate_limit` (CLI-generated).
- Content: `themes`, `tags`, `theme_tags`, `apps`, `collections`, `collection_items`, `favorites`, `theme_stats_daily`.
- Operations: `creator_profiles`, `reports`, `generation_runs`, `uploads`, `site_settings`, `audit_log`, `app_rate_limits`.

The initial migration includes enums, foreign keys, collection constraints, published-only indexes and the stored search vector. `0001_search_extensions.sql` enables `pg_trgm` and adds three trigram indexes. Regenerating the schema after applying these migrations reports no changes. Never use `drizzle-kit push`.

```sh
npm run db:generate
# Read generated SQL before applying it to the intended development branch.
npm run db:migrate
npm run db:studio
npx dotenv -e .env.local -- vitest run tests/integration
```

Better Auth uses Google (once both credentials are configured), bilingual magic-link email, database rate limits, a five-minute session cookie cache and the admin plugin. Session IPs and rate-limit keys are salted SHA-256 hashes. Authenticated deletion removes unpublished owned themes and private dependent records; published themes retain their assets with a null owner. R2 cleanup comes in P11. Email/password sign-in is enabled only for the guarded E2E flag. P03 adds HTTP auth routes and sign-in UI.

Google OAuth and Resend credentials remain unconfigured locally. Resend delivery fails explicitly until `RESEND_API_KEY` and `EMAIL_FROM` are provided; actual mailbox delivery has not been tested. Configure Google and Resend before P03 sign-in testing.

Auth tables are generated by the official `auth@1.7.12` CLI, matching Better Auth 1.7.12; see `docs/02` for first-generation bootstrap and regeneration commands. Domain timestamps use `timestamptz`; generated auth timestamps retain the CLI's UTC representation. Generated auth code is excluded from Prettier.

P01 verification passed: typecheck, lint, production build and all 137 tests, including seven live Neon integration tests. These cover full-text/trigram search, collection constraints, concurrent rate limits, hashed auth identifiers, real credential signup and authenticated deletion with published-theme preservation. Test records are cleaned up by exact IDs. Drizzle Studio starts successfully; database inspection confirms all 20 tables, both migrations and all four search indexes. Manual follow-up: inspect the tables with `npm run db:studio`, then configure Google/Resend before P03 sign-in testing.

## Codemagic build

The root `codemagic.yaml` defines the manual `web-production` workflow: Node 24, clean dependency installation (including development tools and native optional packages), Chakra type generation, typecheck, lint, unit tests, Next.js production build and standalone server packaging. Start it from the public `ahmadalwakai/vibeset` repository after connecting it to Codemagic. No push triggers or publishing steps are configured.

The default Mac mini M2 runner produces `vibeset-web-darwin-arm64.tar.gz` plus a JUnit report. Extract the archive on a compatible Node 24/macOS ARM64 host and run `node server.js`. For a Linux deployment artifact, select an eligible Linux runner in the YAML before building; native modules match the build machine. Codemagic performs the build; hosting remains a separate step.

`NEXT_PUBLIC_SITE_URL` and `NEXT_PUBLIC_CDN_URL` default to the planned production origins in the YAML. Change them before building for another environment because Next.js embeds public variables into the bundle. This P02 shell needs no database or provider secrets to build. Unit tests run in CI; the seven database integration tests require a deliberately configured isolated `TEST_DATABASE_URL`. The workflow never runs migrations, enables test auth, skips environment validation or includes `.env*` files in its artifact.

Codemagic must clone a committed remote revision; local changes cannot be built there until pushed. [Build #2](https://codemagic.io/app/6adbd483898c462c5009d7a6/build/6adbd5834a72334e32e48be6) finished successfully for commit `5673651`: typecheck, lint, 155 passing unit tests, Next.js production build and standalone packaging. Seven database integration tests skipped because no isolated database was configured in CI. The 12.40 MB artifact bundle contains the server archive and JUnit report. The packaged server has not been started on a compatible host.
